# Earshot widgets and system actions

This extension is part of an **experimental, AI-assisted native iOS port of [Earshot by HellzYeahh and contributors](https://github.com/HellzYeahh/earshot)**. The original Android app, configurable tile/widget cycle, protocol research and feature design are their work. Preserve the original MIT licence and [third-party notices](../../THIRD_PARTY_NOTICES.md). This fork is independent of the original project, Bose and Skullcandy.

## What is implemented

- An iOS 17+ Home Screen widget shows the app’s last saved mode and headphone/per-bud/case battery reports, with device-estimated remaining minutes when available. The small widget has a Cycle button; the medium widget has Quiet, Aware and Cycle buttons.
- iOS 18+ Control Center controls provide separate Quiet, Aware and Cycle request buttons. They do not represent a live headphone toggle.
- Ten foreground Shortcuts actions provide Quiet, Aware, Cycle modes, a configured listening mode, cancellation level, hardware three-band EQ, a local EQ preset, a saved listening rule, local EQ cycle, and voice memo start/stop. Local EQ affects only audio played by Earshot.
- Settings → Mode cycle selects configured mode IDs in canonical slot order. Automatic cycling uses configured favourites, then available built-in slots, then other configured modes. Explicit unavailable selections are skipped; an entirely unavailable saved cycle requires repair. The next target is resolved inside the foreground app using this connection’s device reports.

Widget values are snapshots, not a live radio connection. A timestamp and older-snapshot indication appear after five minutes. Demo snapshots say **DEMO** and all their device changes are simulated. A displayed next-mode hint can be stale; the request does not carry that cached target as authority. A missing or stale widget is not evidence of headphone failure.

## Foreground execution and delivery

Widget and control buttons use `OpenEarshotListeningIntent`. Its source belongs to **both the app and widget targets**, as Apple requires for an opening control. It adopts `OpenIntent`, specifies `openAppWhenRun = true` for older systems and `.foreground` supported mode on iOS 26, and requires device authentication. Apple documents that `OpenIntent` opens the app, that foreground mode equals immediate foreground execution, and that widget intents with `openAppWhenRun = true` perform in the app process. These are execution contracts, not evidence that this fork has completed a system-surface acceptance test. [Apple: control buttons](https://developer.apple.com/documentation/widgetkit/creating-controls-to-perform-actions-across-the-system), [OpenIntent](https://developer.apple.com/documentation/appintents/openintent), [foreground mode](https://developer.apple.com/documentation/appintents/intentmodes/foreground), [interactive widget execution](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities).

`perform()` queues a request; it does not claim a headphone accepted it. The app drains requests on activation and on its process-local notification. Actual actions require the app to remain in the foreground, validate the current mode/capability state and, for physical headphone commands, wait for matching device reports. Disconnection, unsupported modes and stale custom selections produce actionable app results. There is no unrestricted background Bluetooth scheduler.

The App Group file queue uses an exclusive cross-process lock and atomic writes. It holds at most 32 pending requests, expires them after 120 seconds and retains up to 128 consumed IDs to reject replay within that retained history. Setting requests replace older requests for the same setting; separate mode-cycle, local-EQ-cycle and memo-toggle taps remain ordered so each can advance from the preceding confirmed mode. Consumption is at most once within the retained ID history: a crash after consumption can lose an action, and queue acceptance is not an execution acknowledgement. Malformed/version-incompatible queue data is quarantined rather than executed.

## Signing and verification limits

The app and extension declare the same `group.dev.earshot.ios` App Group. Physical installation requires a development team, an available registered group and matching provisioning/entitlements for both targets. [Apple: configuring app groups](https://developer.apple.com/documentation/xcode/configuring-app-groups), [App Groups entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.application-groups). A local Simulator ad hoc signature preserves entitlements for the installed-app App Group tests; it is not physical-device provisioning. An unsigned Simulator build previously failed the actual container test, while the locally signed run passed. See the evidence and reproducible signing settings in [iOS validation](../../docs/IOS_VALIDATION.md).

App/extension compilation, intent conformance, shared queue tests and demo UI tests do **not** establish successful Widget gallery installation, actual widget-button/Control Center delivery, Siri recognition, locked-device behaviour or physical headphone effects. System UI probing is diagnostic until the full action and its resulting app state are observed. Signed iPhone acceptance remains required; record the device, OS, signing configuration, system surface, received request and actual result separately from simulated state.

## Actual Simulator system UI evidence

- `WidgetSmallLayoutFinal.xcresult` passed **1/1**, zero failures/skips and Xcode exit 0. The small widget’s Cycle action opened Earshot and changed Quiet to Aware in demo. The test explicitly waits for foreground activation without calling `activate()` on the app’s behalf. A native icon-size menu installs/resizes Earshot’s own tile; repeat runs reuse the appropriate installed size.
- `SystemMediumLayoutFinal.xcresult` passed **2/2**, zero failures/skips, Xcode exit 0: the medium-widget Aware action and actual Control Center Cycle. Both opened Earshot and applied the requested demo state without test-driven activation. The medium case selects simulated QC Earbuds II, checks Left/Right/Case battery labels and requires the header and all three action frames inside the actual native widget viewport.
- Actual exported screenshots were visually inspected. An earlier six-case UI run passed action delivery, but its medium capture exposed a clipped header/buttons. The corrected medium layout uses horizontal mode/profile and battery columns with a compact timestamp/hint/action footer. Percentages retain readable native fonts. Small rendering is separately regression-tested. See [validation](../../docs/IOS_VALIDATION.md) for each final bundle and exact outcomes.

These tests use iPhone 17 Pro / iOS 26.4.1 with local ad hoc signing. Control Center installation was observed through its actual system gallery; all three Earshot gallery entries were visually inspected. The widget’s own native element is captured without unrelated Home Screen apps. Home Screen Widget Gallery search, Siri recognition, locked-device behavior, physical signed-iPhone delivery and actual headphone effects remain unverified.
